# Технический анализ: узкие места, риски и фишки

## 1. УЗКИЕ МЕСТА (Bottlenecks)

---

### 1.1 Блокирующий поиск позиций — главная боль

**Файл:** `services/seo/main.go:74-118`

```go
for _, keyword := range req.Keywords {
    for page := 1; page <= 5; page++ {
        searchResult, err := client.SearchProducts(keyword, page)
```

**Проблема:** Последовательный перебор ключевиков × 5 страниц. Если пользователь отправит 20 ключевиков — это **100 HTTP-запросов последовательно**, каждый по ~1-3 сек. Итого: **до 5 минут ожидания** на один запрос.

**Решение:**
- Параллельный поиск по ключевикам (горутины с семафором)
- Rate limiter: не более 10 параллельных запросов к WB Search API
- Ранний выход: если товар найден на странице 1 — не искать дальше для этого ключевика
- Фоновая проверка через очередь задач, результат в webhook/polling

---

### 1.2 In-memory хранилище — утечка памяти

**Файл:** `services/seo/main.go:20`

```go
positionHistory = map[int64]map[string][]positionRecord{}
```

**Проблема:** История позиций **никогда не очищается**. Каждая проверка добавляет записи в массив. 100 товаров × 50 ключевиков × 6 проверок/день × 30 дней = **900,000 записей** в памяти. При 10 пользователях — OOM через пару недель.

**То же самое во всех сервисах:**
- `collector/main.go:20-23` — salesData, ordersData, stocksData — без лимитов
- `notifications/main.go:20-21` — alerts растут бесконечно

**Решение:**
- Ротация: хранить только последние N записей (например, 90 дней)
- PostgreSQL + партицирование таблиц по дате
- TTL-based cleanup для in-memory до миграции на БД

---

### 1.3 Глобальный Mutex — bottleneck при масштабировании

**Файл:** Все сервисы используют `sync.RWMutex` на глобальных map.

**Проблема:** Один `mu.Lock()` блокирует **всех пользователей**. При записи позиций пользователя A блокируется чтение для пользователя B.

**Решение:**
- Шардирование: `map[userID]*sync.RWMutex` — каждый пользователь со своим мьютексом
- Или `sync.Map` для простых случаев
- Или PostgreSQL с row-level locking (целевое решение)

---

### 1.4 WB Search API — нет кэширования

**Файл:** `services/seo/main.go:77`

Каждый вызов `check-positions` делает живые запросы к WB. Если два пользователя проверяют "платье летнее" с разницей в 5 минут — два одинаковых набора запросов.

**Решение:**
- Redis-кэш результатов поиска: ключ `search:{keyword}:{page}`, TTL 15 минут
- Экономия: при 100 пользователях с пересекающимися ключевиками — **снижение нагрузки на WB API в 10-50x**

---

### 1.5 Gateway — single point of failure

**Файл:** `services/gateway/main.go`

Gateway это единственный прокси без:
- Health-check бэкендов
- Circuit breaker (если SEO сервис упал — Gateway висит 30 сек на timeout)
- Retry логики
- Rate limiting (один пользователь может заDDoSить все сервисы)

---

## 2. ЧТО МОЖЕТ ПОЙТИ НЕ ТАК (Risk Analysis)

---

### 2.1 КРИТИЧЕСКИЙ: WB заблокирует по IP

**Риск:** Wildberries Search API (`search.wb.ru`) — публичный, но с anti-bot защитой. При частых запросах:
- Капча
- HTTP 429 (Too Many Requests)
- Полная блокировка IP

**Файл:** `pkg/wbapi/client.go:199` — используется `User-Agent: Mozilla/5.0`, что выглядит как скрапинг.

**Последствия:** Сервис проверки позиций полностью перестанет работать.

**Митигация:**
- Пул прокси-серверов (ротация IP)
- Рандомизация задержек между запросами (1-3 сек jitter)
- Ротация User-Agent
- Не запрашивать чаще 1 раза в 4 часа для одного ключевика
- Fallback: использовать WB Seller API (аналитика поисковых запросов) вместо парсинга

---

### 2.2 КРИТИЧЕСКИЙ: WB изменит API

**Риск:** Wildberries регулярно меняет API без предупреждения. Endpoint `/exactmatch/ru/common/v4/search` может:
- Сменить URL
- Изменить формат ответа
- Добавить обязательные параметры
- Перейти на v5

**Последствия:** Все SEO-функции сломаются молча (парсинг вернёт пустые результаты).

**Митигация:**
- Health-check: регулярная проверка с известным товаром (если не находится — алерт админу)
- Абстрактный интерфейс `SearchProvider` — легко подменить реализацию
- Версионирование API-клиента
- Мониторинг: если 0 позиций найдено за последние 2 часа — что-то не так

---

### 2.3 ВЫСОКИЙ: Некорректные позиции из-за персонализации

**Риск:** WB показывает **разные результаты** поиска в зависимости от:
- Региона пользователя (Moscow vs Novosibirsk)
- Истории просмотров
- Наличия товара на ближайшем складе
- Времени суток (промо-товары ротируются)

**Последствия:** Позиция "7" в нашем сервисе может быть "25" для реального покупателя.

**Митигация:**
- Передавать `dest` параметр в WB Search (регион)
- Проверять из нескольких регионов (Москва, СПб, Новосибирск)
- Показывать диапазон: "позиция 5-12 (в зависимости от региона)"
- Делать проверки в разное время суток

---

### 2.4 ВЫСОКИЙ: Race condition в notifications

**Файл:** `services/notifications/main.go:228`

```go
func createAlert(...) alert {
    nextID++  // НЕ защищено мьютексом!
```

`nextID++` вызывается внутри `handleGenerate` (который держит Lock), но и в `handleCreate` — где Lock берётся **после** вызова. Потенциальный duplicate ID или data race.

**Решение:** Использовать `atomic.AddInt64(&nextID, 1)` или генерировать UUID.

---

### 2.5 СРЕДНИЙ: JWT секрет в конфиге по умолчанию

**Файл:** В конфиге по умолчанию `wb-analytics-secret-key-change-in-production`.

**Риск:** Если забудут сменить в продакшене — любой может подделать JWT токен.

**Митигация:**
- Генерировать случайный секрет при первом запуске
- Паника при старте, если секрет = дефолтный в production mode
- Вынести в переменные окружения (уже частично сделано, но нет валидации)

---

### 2.6 СРЕДНИЙ: Нет rate limiting на авторизацию

**Файл:** `services/auth/main.go`

Эндпоинт `/api/auth/login` не имеет ограничения по количеству попыток. Brute force пароля.

**Митигация:**
- Rate limiter: 5 попыток / минута на email
- Блокировка аккаунта после 10 неудачных попыток
- CAPTCHA после 3 неудачных попыток

---

### 2.7 СРЕДНИЙ: Collector не валидирует WB API ключ

**Файл:** `services/collector/main.go:62-69`

```go
if req.APIKey == "" {
    httpError(w, "api_key required", http.StatusBadRequest)
}
userAPIKeys[userID] = req.APIKey  // сохраняем без проверки
```

Пользователь может вставить невалидный ключ, и узнает об этом только при sync (с непонятной ошибкой 502).

**Решение:** При регистрации ключа делать тестовый запрос к WB API.

---

### 2.8 НИЗКИЙ: Нет graceful shutdown

Ни один сервис не обрабатывает SIGTERM/SIGINT. При перезапуске контейнера:
- Текущие HTTP-запросы обрываются
- In-memory данные теряются без предупреждения
